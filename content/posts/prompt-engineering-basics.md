프롬프트 엔지니어링은 AI에게 말을 잘 거는 기술이라기보다, **작업의 목표와 판단 기준을 명확한 입력으로 바꾸는 설계 작업**에 가깝습니다. 같은 모델을 쓰더라도 프롬프트에 맥락, 출력 형식, 제약 조건, 검증 기준이 들어가면 결과의 일관성이 크게 달라집니다.

이 글에서는 개발자가 바로 적용할 수 있는 프롬프트 구조와 반복 개선 방법을 정리합니다.

## 프롬프트 엔지니어링이 필요한 순간

간단한 질문은 짧게 물어도 충분합니다. 하지만 다음 상황에서는 프롬프트를 구조화하는 편이 좋습니다.

- 결과물의 형식이 중요할 때
- 코드, 문서, 기획안처럼 수정 비용이 있는 작업을 맡길 때
- 여러 제약 조건을 동시에 만족해야 할 때
- 답변 품질을 반복해서 재현해야 할 때
- 팀원이 같은 방식으로 AI를 사용해야 할 때

프롬프트가 모호하면 모델은 빈칸을 추측으로 채웁니다. 반대로 좋은 프롬프트는 모델이 추측해야 하는 영역을 줄이고, 사용자가 원하는 판단 기준을 앞에 놓습니다.

## 기본 구조

실무에서 쓰기 좋은 프롬프트는 보통 다음 다섯 가지 요소로 구성됩니다.

```text
역할: 너는 어떤 관점으로 답해야 하는가?
목표: 무엇을 완성해야 하는가?
맥락: 어떤 배경 정보가 중요한가?
제약: 지켜야 할 조건은 무엇인가?
출력: 어떤 형식으로 답해야 하는가?
```

예를 들어 블로그 글 초안을 요청한다면 이렇게 쓸 수 있습니다.

```text
너는 개발자 대상 기술 블로그 에디터야.

주제는 프롬프트 엔지니어링이고, 독자는 AI 도구를 업무에 쓰기 시작한 주니어 개발자야.
목표는 프롬프트를 구조화하는 방법을 실무 예시와 함께 설명하는 글 초안을 만드는 것이야.

조건:
- 한국어로 작성
- 제목 3개 제안
- H2/H3 구조 포함
- 추상적인 조언보다 실제 프롬프트 예시를 우선
- 확인되지 않은 성능 수치나 과장 표현 금지

출력은 Markdown으로 작성해줘.
```

이 정도만 넣어도 "좋은 글 써줘"보다 훨씬 안정적인 결과가 나옵니다.

## 역할은 관점을 정한다

역할은 모델에게 답변의 관점을 지정합니다. 단순히 "전문가처럼 답해줘"보다 구체적인 역할이 좋습니다.

좋은 역할 예시는 다음과 같습니다.

- "너는 보안 리뷰를 맡은 시니어 백엔드 엔지니어야."
- "너는 초보자를 가르치는 TypeScript 튜터야."
- "너는 검색 유입을 고려하는 기술 블로그 에디터야."

역할이 구체적이면 모델이 무엇을 중요하게 봐야 하는지 더 잘 맞춥니다. 보안 리뷰어라면 위험과 악용 가능성을 먼저 보고, 튜터라면 개념 설명과 예제를 우선합니다.

## 맥락은 답변의 정확도를 만든다

모델은 사용자의 프로젝트, 독자, 의도, 기존 코드 스타일을 자동으로 알 수 없습니다. 그래서 필요한 맥락은 프롬프트 안에 직접 넣어야 합니다.

코드 리뷰를 요청할 때는 다음 정보가 도움이 됩니다.

- 변경 목적
- 관련 파일
- 기대 동작
- 현재 실패 증상
- 피하고 싶은 변경 범위

예시는 다음과 같습니다.

```text
아래 React 컴포넌트를 리뷰해줘.

맥락:
- 이 컴포넌트는 블로그 포스트 목록에서 검색과 태그 필터를 처리해.
- 검색어는 title, description, tags에 적용돼야 해.
- 지금은 UI를 크게 바꾸지 않고 버그와 유지보수성만 보고 싶어.

출력:
- 심각도 순서로 문제를 정리
- 파일/라인 기준으로 설명
- 수정 방향은 짧게 제안
```

맥락을 잘 주면 모델은 덜 일반적인 답을 하고, 현재 작업에 맞는 판단을 내릴 가능성이 높아집니다.

## 제약 조건은 결과를 다듬는다

좋은 프롬프트는 "무엇을 해라"뿐 아니라 "무엇을 하지 말라"도 포함합니다. 제약 조건은 결과물의 품질을 일정하게 만드는 장치입니다.

예를 들어 코드 생성을 맡길 때는 다음 제약이 유용합니다.

- 기존 파일 구조를 유지할 것
- 새 라이브러리는 추가하지 말 것
- 타입 에러가 나지 않게 작성할 것
- 사용자 입력 검증을 포함할 것
- 테스트 가능한 단위로 분리할 것

제약 조건은 너무 많으면 오히려 충돌할 수 있습니다. 우선순위가 있는 조건은 "가장 중요", "가능하면"처럼 강도를 구분해서 적는 것이 좋습니다.

## 예시는 가장 강한 힌트다

모델에게 원하는 스타일이 있다면 설명보다 예시가 더 빠릅니다.

나쁜 요청:

```text
간결하고 실무적인 느낌으로 써줘.
```

더 나은 요청:

```text
아래 문체를 따라 써줘.

예시:
"이 설정은 빌드를 빠르게 만들기보다, 실패 원인을 빨리 찾게 해준다. 팀 프로젝트에서는 속도보다 재현성이 더 중요할 때가 많다."

이런 식으로 과장 없이, 판단 기준과 이유를 함께 설명해줘.
```

예시는 출력 형식에도 쓸 수 있습니다. JSON, 표, 릴리즈 노트, 커밋 메시지처럼 형식이 중요한 작업에서는 짧은 샘플을 넣는 것이 가장 확실합니다.

## 검증 기준을 함께 요청하기

프롬프트 엔지니어링에서 자주 빠지는 부분은 검증입니다. 결과를 받은 뒤 "괜찮아 보인다"로 끝내면 품질이 흔들립니다.

다음처럼 검증 기준을 함께 요청할 수 있습니다.

```text
답변 마지막에 자체 점검 목록을 추가해줘.

점검 항목:
- 요구한 출력 형식을 지켰는가?
- 확인되지 않은 주장을 만들지 않았는가?
- 초보자가 따라 할 수 있는 예시가 있는가?
- 다음 작업으로 이어질 수 있는 구체적인 제안이 있는가?
```

특히 코드, 법률, 의료, 금융, 최신 API처럼 오류 비용이 큰 영역에서는 모델의 답을 최종 사실로 취급하지 말고 별도 검증 과정을 둬야 합니다.

## 반복 개선 루프

처음부터 완벽한 프롬프트를 만들 필요는 없습니다. 좋은 프롬프트는 보통 다음 순서로 다듬어집니다.

1. 짧은 프롬프트로 초안을 얻는다.
2. 결과에서 부족한 부분을 찾는다.
3. 부족한 부분을 제약 조건이나 예시로 추가한다.
4. 다시 실행해서 재현성을 확인한다.
5. 자주 쓰는 형태는 템플릿으로 저장한다.

반복할 때는 "더 좋게 해줘"보다 구체적인 피드백이 좋습니다.

```text
좋아. 다만 예시가 너무 일반적이야.
Next.js 블로그 프로젝트를 예로 들어서, Markdown 포스트 생성 프롬프트로 다시 써줘.
출력은 바로 복사해서 쓸 수 있는 프롬프트 블록 하나만 제공해줘.
```

이렇게 피드백하면 모델은 수정 방향을 명확히 이해합니다.

## 바로 쓰는 프롬프트 템플릿

아래 템플릿은 대부분의 작업에 맞게 변형할 수 있습니다.

```text
너는 [역할]이야.

목표:
- [완성해야 하는 결과]

맥락:
- [대상 독자, 프로젝트 배경, 현재 상황]
- [중요한 파일, 데이터, 제약]

조건:
- [반드시 지킬 조건]
- [피해야 할 것]
- [우선순위]

출력 형식:
- [Markdown, JSON, 표, 단계별 목록 등]

마지막에 다음을 점검해줘:
- 요구사항을 모두 반영했는가?
- 불확실한 부분을 명확히 표시했는가?
- 다음 행동이 분명한가?
```

이 템플릿의 핵심은 모델에게 "좋은 답"의 기준을 맡기지 않는 것입니다. 사용자가 기준을 줄수록 결과는 더 예측 가능해집니다.

## 마무리

프롬프트 엔지니어링은 특별한 문구를 외우는 일이 아닙니다. 목표, 맥락, 제약, 예시, 검증 기준을 명확히 적어 모델이 추측해야 할 공간을 줄이는 일입니다.

처음에는 템플릿을 쓰고, 반복되는 작업은 팀이나 프로젝트에 맞게 조금씩 다듬어보세요. 좋은 프롬프트는 한 번의 멋진 답변보다, 여러 번 실행해도 흔들리지 않는 결과를 만드는 쪽에 가깝습니다.
